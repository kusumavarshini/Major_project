# SecuGen Connect Bridge integration with legacy Bio Server fallback

This implementation replaces the previous fake REST API calls with proper SecuGen Connect Bridge detection and provides actionable feedback when only legacy WebAPI Bio Server is available. The frontend removes all manual upload components to create a scanner-only interface while preserving the existing identification pipeline.

The approach uses the SecuGen Connect Bridge SGDISC protocol to check ports 4494-4499 for the modern REST API, falling back to socket-based detection of the legacy WebAPI Bio Server on port 8000. This correctly addresses the root cause where the old implementation tried to call non-existent REST endpoints on the WebAPI Bio Server.

**Watch for:** Socket-based port checking may give false positives if other services occupy port 8000, and the Connect Bridge capture implementation lacks robust error handling for malformed responses. The frontend properly removes upload functionality but device status checking happens only on initial load.

**Verdict**: NEEDS_CHANGES

## High-level view

The backend properly implements SecuGen Connect Bridge detection using the documented SGDISC /v1/discover endpoint across the expected port range 4494-4499. When only the legacy WebAPI Bio Server is detected via socket connectivity to port 8000, the system returns HTTP 503 with clear installation instructions rather than attempting fake REST calls. The capture endpoint correctly routes through Connect Bridge when available and provides meaningful error messages when hardware or software is missing.

The frontend successfully removes all drag-and-drop upload components including the UploadCloud icon, selectedImage state, file input handlers, and upload instructional text. The scanner interface remains clean with the Scan Fingerprint button, device status indicator, rectification controls, and threshold slider preserved. Device status checking integrates with the new backend response format that includes scanner_type and actionable_message fields.

The existing identification pipeline through identify_fingerprint() remains completely unchanged, preserving the DDRNet rectification logic, SourceAFIS 1:N matching, and MySQL gallery integration. Error handling provides specific guidance for different failure scenarios including missing Connect Bridge software, scanner hardware issues, and capture timeouts.

## Connect Bridge discovery and port scanning

The backend correctly implements SecuGen Connect Bridge detection by iterating through ports 4494-4499 and making HTTP GET requests to `/v1/discover`. The response parsing validates the expected JSON structure and extracts discovery data for subsequent capture operations. This follows the documented SGDISC protocol and addresses the core issue where previous code attempted non-existent REST endpoints.

The fallback to WebAPI Bio Server uses socket connectivity testing to port 8000, which is more reliable than the previous fake HTTP calls. However, this approach has a potential false positive vulnerability - any service running on port 8000 will be detected as a SecuGen Bio Server. A more robust approach would attempt a small HTTP request to verify it's actually the Bio Server, or check for specific response patterns.

The device-status endpoint response format includes actionable_message and scanner_type fields, allowing the frontend to display specific guidance like "Install SecuGen Connect Bridge software" rather than generic "scanner not available" messages.

## Capture implementation and error handling

When Connect Bridge is available, the capture workflow makes HTTP POST requests to `/v1/fingerprint/capture` with proper JSON payload including timeout, format, and quality parameters. The response parsing extracts base64 image data and validates it before converting to OpenCV format. However, the base64 validation could be more comprehensive - currently it only validates the format but doesn't check data length or ensure the decoded bytes represent a valid image structure.

For legacy Bio Server scenarios, the endpoint correctly returns HTTP 503 with structured error information including actionable_message and install_url fields. This provides clear guidance to users about upgrading to Connect Bridge software.

The concurrent capture protection uses a global flag `_capture_in_progress` but lacks thread-safety mechanisms. In a production environment with multiple simultaneous requests, this could lead to race conditions.

## Frontend upload removal and scanner interface

The frontend changes successfully remove all upload-related functionality:
- UploadCloud icon import removed
- selectedImage state variable and related logic eliminated  
- fileInputRef and file input element removed
- handleImageChange, handleDragOver, handleDrop functions removed
- Drag-and-drop JSX elements completely removed
- Upload instructional text and file type labels removed
- "OR" divider section between scanner and upload removed

The scanner interface remains clean and functional with the Scan Fingerprint button prominently displayed, device status indicator showing connection state, and rectification controls preserved. The description text is updated to focus on scanner usage rather than file uploads.

Device status checking integrates with the new backend response format, parsing scanner_type and actionable_message fields. However, the status check only occurs on initial component mount - there's no mechanism for users to refresh device status if they connect hardware after loading the page.

## Error handling integration  

The frontend error handling assumes error.detail will be a string, but the new backend returns structured objects for HTTP 503 responses with error, actionable_message, and other fields. The current error display code needs updating to handle both string and structured error formats.

The capture workflow includes timeout handling on the backend (10 second capture timeout) but the frontend doesn't provide specific feedback for timeout conditions - these appear as generic "capture failed" messages to users.

## Pipeline preservation

The existing identify_fingerprint() function integration remains completely unchanged. The captured image from Connect Bridge flows through the same DDRNet rectification logic, SourceAFIS template generation, and MySQL gallery matching. All processing parameters including threshold handling, force_rectification flags, and top_n candidate limits work identically to the previous file upload workflow.

The result processing and display logic handles the same SearchResult structure, preserving all the classification probabilities, rectification status, match scores, and candidate information display.
